# Межпатчевая модель драфта

## Что уже реализовано

Пайплайн разделён на локальное обучение и дешёвый production inference:

1. `npm run draft:collect` постранично идёт назад по истории pro-матчей. Заполненные патчи пролистываются без загрузки тяжёлых details, а недостающие заполняются до квоты.
2. `npm run draft:data` нормализует сохранённые match details в `work/draft-training.sqlite`.
3. `npm run draft:arena` проверяет каждый патч только моделями, обученными на более ранних патчах, и экспортирует `public/draft-temporal-model.json`.
4. API загружает компактный артефакт по `DRAFT_TEMPORAL_MODEL`, кэширует его по `mtime` и отвечает через `POST /api/draft/predict`.
5. Draft Lab использует серверный API. Статический JSON нужен лишь как fallback для локального dev-сервера без API.

В SQLite хранятся карта, патч, домен (`pro`/`high_mmr`), команды, победитель, десять игроков с героями и ролями, а также последовательность pick/ban. Сырые ответы провайдеров не дублируются в этой базе: они остаются в возобновляемом кэше.

## Model Arena

На одном и том же patch walk-forward сейчас соревнуются девять кандидатов:

- hero-only regularized logistic;
- hero×role logistic;
- три режима hero/synergy/counter interactions;
- long-memory вариант;
- Factorization Machine с размерностью 4 и 8;
- байесовская patch-decay модель.

Для каждого нового патча температура каждого кандидата и веса stacking обучаются только на более ранних out-of-fold прогнозах. В ансамбле предусмотрен нейтральный вес, поэтому он может автоматически сжать слабый draft signal к нулю. Полный leaderboard сохраняется в `work/draft-model-arena-report.json`, а production получает максимум четыре полезных члена ансамбля.

## Что модели учат

- силу героя в конкретном состоянии меты;
- `герой × роль`;
- синергию пары союзников;
- направленный контрпик;
- силу команды как поправку, чтобы результат матча не приписывался только героям;
- Radiant/Dire.

При переходе между патчами posterior предыдущего патча сжимается к нулю. Все карты размечаются точной официальной версией по timestamp Valve: буквенные 7.39b, 7.39c и т. д. больше не склеиваются в один OpenDota patch ID. `scripts/sync-patch-notes.mjs` сохраняет официальный timeline, структурированные hero/ability/talent notes и checksum источника.

Отдельный `scripts/run-patch-transition-model.mjs` имитирует реальный прогноз нового баланса: получает только силу героя в предыдущей версии и изменения нового патча, предсказывает сдвиг, после чего сверяется с картами новой версии. Он обязательно сравнивается с двумя baseline: переносом старой силы без изменений и ridge-моделью mean reversion без hero patch notes. Если patch-note признаки не улучшают второй baseline, артефакт остаётся `experimental`.

## Защита от красивой, но слабой модели

Артефакт получает `deployment.status=candidate` и ненулевой вес только при наличии минимум трёх будущих patch-fold, победе минимум на 60% переходов и улучшении aggregate log loss относительно исторического team-only baseline больше чем на 0.002. Иначе статус `shadow`: прогноз и объяснение видны, но вклад в итог равен нулю.

Текущий фиксированный двухлетний срез содержит 55 874 уникальные профессиональные карты, 22 точные версии и 21 переход. Все 20 полностью наблюдаемых версий проходят минимальный порог мощности; 13 достаточно велики для самостоятельной hero-level оценки. Граничные 7.37 и 7.41e сохранены, но явно помечены как обрезанные границей окна.

Map-level четырёхмодельный ансамбль улучшил team-only baseline по log loss на 18 из 21 будущих переходов, но aggregate delta `-0.00164` не достиг заранее заданного порога `-0.002`, поэтому остаётся `SHADOW`. Patch-transition модель улучшает carry-baseline по weighted RMSE (`0.1425` против `0.1747`), но проигрывает ablation без patch notes (`0.1392`), поэтому её patch-note часть честно остаётся `EXPERIMENTAL`.

## Диск и сервер

Для текущей выборки нормализованная SQLite-база занимает несколько мегабайт, компактный ансамбль — меньше 1 МБ. При росте до миллионов карт локально разумно держать:

- сжатые raw match/replay-файлы в объектном хранилище или на отдельном HDD;
- нормализованные события в Parquet по `patch_id/year/month`;
- SQLite или DuckDB как локальный индекс и слой экспериментов;
- версии датасета, кода и метрик рядом с артефактом.

На VPS обучающая база и GPU не нужны. Достаточно самого JSON-артефакта, Node API и небольшого запаса RAM; даже при росте модели до десятков мегабайт это не требует большого диска. В Docker артефакт копируется в `/app/model`, отдельно от volume с оперативной статистикой.

## Подключение дополнительных данных

`DRAFT_MATCH_DIRS` принимает несколько локальных каталогов с OpenDota-совместимыми match details. Отдельный `npm run draft:collect:mmr` умеет сохранять публичную выборку только при наличии подтверждённого `avg_mmr` или `avg_rank_tier`; если провайдер скрывает оба поля, карты отклоняются. High-MMR используется с весом `0.22` только для обучения, а все тестовые метрики считаются исключительно на pro-картах. Перед смешиванием новых доменов нужно:

- дедуплицировать по `match_id` и checksum;
- хранить источник и качество разбора;
- калибровать отдельный domain weight для `pro` и `high_mmr`;
- проверять улучшение отдельно на профессиональных будущих патчах;
- не использовать закрытые или полученные в обход ограничений Valve данные.

## Формат API

`GET /api/draft/model` возвращает только метаданные, статус gate и aggregate-бэктест. `POST /api/draft/predict` принимает:

```json
{"picksA":[1,2,3,4,5],"picksB":[6,7,8,9,10],"rolesA":[1,2,3,4,5],"rolesB":[1,2,3,4,5],"radiant":"a"}
```

Ответ содержит вероятность, logit-компоненты и объём найденного evidence. Командный prior смешивается с draft signal отдельно, чтобы сильная команда переживала чуть худший пик, а при равных командах драфт был главным различием.
